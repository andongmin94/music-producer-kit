# Review and completion

Keep three evaluations distinct.

## Request compliance

Compare result with the current brief, requested edit range and protected material.
A whole song is not complete when only a short loop exists. A lyrics-only task is not improved by unsolicited DAW changes.
For references and humming, separate observed input features from assumptions and extraction errors.

## Technical checks

Read files or Live state after writing. Check note timing/ranges, track identity, missing sources, relevant controls, export duration and saved versions.
For MIDI-helper patches, use the inspected source SHA and inspect the resulting MIDI. Hash checks cover serialized MIDI events, not all Live state.
For an .als deliverable, save/reopen and verify actual devices, source references and editability.
Do not assign quality points for borrowed chords, asymmetry, irregular fills, variable width or imperfect pitch.

## Listening and preference

Only claim listening when an audio-capable path actually inspected the rendered sound.
Signal measurements, a running transport and valid note data are different evidence.
When comparison is possible, compare relevant versions at suitable levels and ask for the user's preference at a useful decision point.
Do not require an approval between every microstep when whole-draft production was delegated.
If an improvement is unclear, keep the previous version instead of adding complexity to satisfy a checklist.

## Delivery note

Say what changed, what remained protected, where the editable outputs were saved, and which checks were run.
List important unsupported/unrun operations. Never use a general 'all passed' to hide untested audio or host behavior.
Keep a brief private session.md with current files and approved decisions so subsequent turns can resume from actual state.
